# Контракт бреше: OpenAPI проти реальної поведінки

Демо до доповіді Інни Осінної «Контракт бреше: OpenAPI проти реальної поведінки»
на конференції Бетельгейзе 2026. Це маленький сервіс бронювання квитків з написаним руками
контрактом [`openapi.yaml`](openapi.yaml) і перемикачем «дрейфу». Коли дрейф увімкнено, сервіс
поводиться не так, як обіцяє контракт. Демо показує, які з цих розходжень помічають звичайні
тести в Postman, валідація схеми, поведінковий тест і Schemathesis, а які — ні.

## Що потрібно

- Docker з Docker Compose — щоб запустити сервіс.
- Postman — для основних перевірок.
- Python 3.12+ — для Schemathesis і pytest-тестів (необовʼязково).
- Node.js — тільки якщо хочете запускати Postman-колекцію з командного рядка через Newman (необовʼязково).

## Запуск

```bash
docker compose up
```

Сервіс працює на `http://localhost:8000`. Дані зберігаються в памʼяті, база не потрібна.

## Postman-колекція

1. Postman → **Import** → виберіть файл [`postman/collection.json`](postman/collection.json).
2. У змінних колекції `baseUrl` уже стоїть `http://localhost:8000`.
3. Запускайте папки через **Run collection** (Collection Runner) або окремі запити через **Send**.

| Папка | Що робить |
|---|---|
| 0. Керування демо | перемикачі дрейфу і «сирих» помилок, скидання даних, поточний стан |
| 1. Звичайні тести | статус 200 і пара полів — як зазвичай пишуть тести. Без негативних кейсів |
| 2. Валідація схеми | ті самі 3 запити + повторне бронювання того самого місця. Кожна відповідь звіряється з JSON-схемою з контракту, обраною за статус-кодом |
| 3. Поведінка | забронювати місце, потім те саме ще раз → очікуємо 409 |

- Схеми в папці 2 — точний переклад компонентів `openapi.yaml`. Вони лежать у змінних колекції
  `schemaEvents`, `schemaSeats`, `schemaBooking`, `schemaError`.
- Перевірка схеми — один скрипт на рівні папки 2 (папка → Scripts → Post-response). Він використовує
  вбудований у Postman `ajv` і показує помилки у вигляді «шлях: має бути X, прийшло Y».
  Якщо статус-код не описаний у контракті, тест падає з повідомленням `статус N не описаний у контракті`.
- Запити бронювання перед відправкою самі скидають дані, тому результат не залежить від попередніх запусків.

Те саме з командного рядка:

```bash
npx newman run postman/collection.json --folder "2. Валідація схеми"
```

## Перемикачі: дрейф і «сирі» помилки

Перемикаються без перезапуску сервісу — запитами з папки «0. Керування демо» або через curl.
Ці службові ендпоінти не входять у контракт.

| Що | Запит |
|---|---|
| Увімкнути / вимкнути дрейф | `POST /_admin/drift` `{"enabled": true\|false}` |
| Увімкнути / вимкнути «сирі» помилки | `POST /_admin/raw-errors` `{"enabled": true\|false}` |
| Скинути дані (всі місця вільні) | `POST /_admin/reset` |
| Поточний стан | `GET /_admin/state` → `{"drift": …, "raw_errors": …}` |

```bash
curl -X POST localhost:8000/_admin/drift -H 'Content-Type: application/json' -d '{"enabled": true}'
```

Початкові значення можна задати при старті: `DRIFT=1 docker compose up`, `RAW_ERRORS=1 docker compose up`.
Перемикачі незалежні.

**Дрейф** вмикає чотири розходження з контрактом (таблиця нижче).

**«Сирі» помилки.** За замовчуванням сервіс повертає помилки фреймворку у форматі `Error` з контракту,
а помилку валідації запиту — як задокументований 400. З увімкненим перемикачем FastAPI відповідає
як за замовчуванням: 422 з `{"detail": [...]}`, якого немає в контракті. Так виглядав сервіс до того,
як Schemathesis знайшов ці відповіді й їх виправили.

## Schemathesis

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
curl -X POST localhost:8000/_admin/reset
.venv/bin/st run openapi.yaml --url http://localhost:8000 --checks all
```

Перед прогоном варто скинути дані: Schemathesis бронює місця.

## Чотири розходження і що їх ловить

| # | Ендпоінт | Що повертає сервіс з дрейфом | Що каже контракт |
|---|---|---|---|
| 1 | `GET /events/{id}/seats` | `row` рядком: `"1"`, `"2"`, … | integer |
| 2 | `POST /bookings` | `status: "PENDING_PAYMENT"` | enum `CONFIRMED` / `CANCELLED` |
| 3 | `GET /events` | у події 2 `venue: null` | required, не nullable |
| 4 | `POST /bookings` на зайняте місце | **200** з `{"error": "SEAT_TAKEN", ...}` | 409 + Error |

| # | Звичайні тести (папка 1) | Валідація схеми (папка 2) | Поведінка (папка 3) | Schemathesis |
|---|---|---|---|---|
| 1 `row` рядком | ❌ не ловлять | ✅ | — | ✅ |
| 2 `PENDING_PAYMENT` | ❌ | ✅ | — | ✅ |
| 3 `venue: null` | ❌ | ✅ | — | ✅ |
| 4 200 замість 409 | ❌ (негативного кейсу немає) | ❌ | ✅ | ❌ |

Чому кейс 4 проходить валідацію схеми: схема `Booking` у контракті навмисно «мʼяка» — без `required`
і без заборони додаткових полів (див. коментар в `openapi.yaml`). Тіло помилки з кодом 200 формально
підходить під таку схему, а 200 — задокументований код. Помітити це може тільки тест, який знає,
як сервіс має поводитися.

## Покроковий сценарій

1. Дрейф вимкнено. Postman, папка «1. Звичайні тести» → усе зелене.
2. «Увімкнути «сирі» помилки» → Schemathesis → знахідки «Undocumented HTTP status code» (422).
   Це швидкий фідбек на документацію. Потім «Вимкнути «сирі» помилки».
3. «Увімкнути дрейф», «Скинути дані» → Postman, папка 1 → усе ще зелене.
4. «Скинути дані» → Schemathesis → 3 знахідки «Response violates schema» (venue, row, status).
5. Postman, папка «2. Валідація схеми» → 3 червоні, 1 зелений (повторне бронювання).
6. Postman, папка 3: Send «Забронювати місце», потім Send «Забронювати те саме місце ще раз» →
   **200** з `{"error": "SEAT_TAKEN", ...}`. Запит з папки 1 для цього не підходить: він сам скидає дані.
7. Postman, папка «3. Поведінка» → червоний: очікували 409, прийшло 200.

Наостанок: «Вимкнути дрейф», «Скинути дані».

## Фактичні результати прогонів

Версії: FastAPI 0.143.1, Schemathesis 4.31.0, Newman 6.2.3, openapi-core 0.23.1.

### Postman (Newman, кожна папка окремо)

| Папка | Дрейф вимкнено | Дрейф увімкнено |
|---|---|---|
| 1. Звичайні тести | 7 перевірок пройшли | **7 пройшли** |
| 2. Валідація схеми | 4 пройшли | **3 впали** (venue, row, status), **1 пройшла** (повторне бронювання) |
| 3. Поведінка | 1 пройшла | **1 впала**: `expected response to have status code 409 but got 200` |

Вивід папки 2 з дрейфом:

```
1. GET /events → 200 відповідає контракту
   [1].venue: має бути string, прийшло null

2. GET /events/{id}/seats → 200 відповідає контракту
   [0].row: має бути integer, прийшло "1"
   [1].row: має бути integer, прийшло "1"
   [2].row: має бути integer, прийшло "1"
   ... і ще 9 таких самих

3. POST /bookings → 200 відповідає контракту
   status: має бути одне з CONFIRMED / CANCELLED, прийшло "PENDING_PAYMENT"

✓  POST /bookings → 200 відповідає контракту      ← повторне бронювання
```

### Schemathesis (`--checks all`)

| Режим | Результат |
|---|---|
| дрейф вимкнено, «сирі» помилки вимкнено | `No issues found`, exit 0 |
| дрейф вимкнено, **«сирі» помилки увімкнено** | 2 знахідки стабільно (+1 іноді), exit 1 |
| **дрейф увімкнено**, «сирі» помилки вимкнено | 3 знахідки, кейс 4 не знайдено, exit 1 |

**«Сирі» помилки увімкнено:**

- `GET /events/{event_id}/seats` — **Undocumented HTTP status code**: `Received: 422`, `Documented: 200, 400, 404`
- `POST /bookings` — **Undocumented HTTP status code**: `Received: 422`, `Documented: 200, 400, 404, 409`
- Іноді (приблизно в третині прогонів), у розділі `Stateful tests` — **Response violates schema**:
  `"error" is a required property` для тіла `{"detail":"There was an error parsing the body"}`
  (400 на тіло, яке не вдається розібрати як JSON).

**Дрейф увімкнено** (однаково в усіх прогонах):

- `GET /events` — **Response violates schema**: `null is not of type "string"`
- `GET /events/{event_id}/seats` — **Response violates schema**: `"1" is not of type "integer"`
- `POST /bookings` — **Response violates schema**: `"PENDING_PAYMENT" is not one of "CONFIRMED" or "CANCELLED"`
- Кейс 4 (200 + Error на зайняте місце) **не знайдено**, хоча під час прогону місця реально бронювались повторно.

Примітки:
- У підсумку Schemathesis іноді буває `1 errored`, навіть у чистому прогоні з exit 0. Це не знахідка.
- Попередження «Missing test data» для `POST /bookings` (більшість згенерованих id дають 404) — теж не знахідка.

## Для автоматизаторів: те саме на pytest

Ті самі три види перевірок, тільки в коді. Адреса сервісу — зі змінної `BASE_URL`
(за замовчуванням `http://localhost:8000`). Перед кожним тестом дані скидаються; режим дрейфу
тести не перемикають — вмикайте його самі.

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/pytest tests/test_naive.py -v
.venv/bin/pytest tests/test_schema.py -v --tb=short
.venv/bin/pytest tests/test_behavior.py -v
```

- `test_naive.py` — статус-код і наявність кількох полів, без негативного кейсу.
- `test_schema.py` — ті самі запити + валідація відповіді проти `openapi.yaml` (openapi-core).
  Обгортка [`tests/contract.py`](tests/contract.py) друкує «шлях до поля: причина».
- `test_behavior.py` — повторне бронювання повертає 409.

| Набір | Дрейф вимкнено | Дрейф увімкнено |
|---|---|---|
| `test_naive.py` | 3 passed | **3 passed** |
| `test_schema.py` | 4 passed | **3 failed** (venue, row, status), 1 passed |
| `test_behavior.py` | 1 passed | **1 failed** (`assert 200 == 409`) |
